## 2. 추진 배경

Smart Factory의 생산설비는 모터, 베어링, 펌프, 컨베이어, 압축기와 같은 회전체 및 구동장치로 구성된다. 이들 장비는 장시간 운전과 반복부하로 인해 마모, 불균형, 정렬불량, 윤활부족, 과열 및 전기적 이상이 점진적으로 발생할 수 있다.

현장의 정기점검 방식은 점검주기 사이에 발생하는 이상을 조기에 발견하기 어렵고, 고장 후 정비 방식은 생산중단, 긴급부품 조달, 납기지연 및 품질저하를 유발한다. 설비 담당자의 경험에 의존한 진단은 담당자별 편차가 크며, 여러 시스템에 분산된 센서 데이터와 정비이력이 통합되지 않아 장기적인 상태변화를 분석하기 어렵다.

따라서 설비 데이터를 지속적으로 수집하고, 이상징후를 조기에 탐지하며, 고장가능성과 정비 우선순위를 작업자와 정비 담당자에게 제공하는 예지보전 시스템이 필요하다.

## 3. 현행 문제정의

| ID | 현행 문제 | 원인 | 영향 |
|---|---|---|---|
| PB-01 | 설비 이상징후를 고장 전에 발견하기 어려움 | 정기점검과 작업자 육안점검 중심 | 돌발고장과 생산중단 증가 |
| PB-02 | 센서 데이터의 장기 추세 분석이 어려움 | 데이터가 PLC, 파일, 장비별 도구에 분산 | 열화패턴과 고장원인 분석 제한 |
| PB-03 | 경보가 많고 중요도 구분이 부족함 | 단순 임계값과 설비별 상이한 기준 | 경보 피로와 중요경보 누락 |
| PB-04 | 정비 우선순위 결정이 경험에 의존함 | 고장확률, 생산영향, 정비이력 통합 부족 | 불필요한 정비 또는 정비지연 |
| PB-05 | AI 모델의 성능과 적용근거를 확인하기 어려움 | 데이터·특징·버전·평가지표 관리 부족 | 모델 신뢰성과 재현성 저하 |
| PB-06 | 설비·사용자·권한 변경이 체계적으로 관리되지 않음 | 통합관리 기능과 감사기록 부족 | 보안 및 운영오류 위험 증가 |

## 4. 목표 시스템 개념

목표 시스템은 설비 센서 데이터를 IoT Gateway를 통해 수집하고, 메시지 전송, 데이터 검증, 시계열 저장, 상태 시각화 및 AI 분석을 수행한다. 위험이 탐지되면 설비, 위험수준, 추정원인과 권고조치를 포함한 경보를 제공한다. 작업자와 정비 담당자의 확인·조치 결과는 정비이력에 저장되고 AI 모델 개선에 활용된다.

### 4.1 목표 운영흐름

1. 센서가 진동, 온도, 전류, 회전속도 데이터를 측정한다.
2. IoT Gateway가 데이터를 표준 메시지로 변환하여 전송한다.
3. 시스템이 데이터 형식, 시간, 범위 및 누락 여부를 검증한다.
4. 정상 데이터는 시계열 데이터베이스에 저장된다.
5. 규칙 기반 분석과 AI 모델이 설비상태와 고장징후를 평가한다.
6. 경고 또는 위험상태가 탐지되면 Dashboard와 알림을 제공한다.
7. 정비 담당자가 센서추세, 이력 및 권고조치를 검토한다.
8. 조치결과가 기록되고 향후 모델 재학습과 기준개선에 사용된다.

## 6. 시스템 범위

### 6.1 포함범위

- 설비 및 센서 등록·식별·상태관리
- 진동, 온도, 전류, 회전속도 등 센서 데이터 수집
- 데이터 유효성 검사, 단위 변환, 타임스탬프 정규화
- 메시지 전송, 시계열 저장, 조회 및 시각화
- 규칙 기반 이상탐지와 학생이 직접 개발하는 AI 예지보전 모델 연동
- 경보 생성, 우선순위, 확인, 담당자 지정 및 종료관리
- 정비 권고, 작업결과, 고장원인 및 정비이력 관리
- 사용자, 역할, 접근권한, 감사로그 및 시스템 상태관리
- 모델·데이터·특징·평가결과 버전관리 개념
- OSS 검색·평가·선정 및 통합 아키텍처 설계

### 6.2 제외범위

- 실제 생산설비 개조와 센서 구매·설치·배선
- PLC 제어로직 및 안전제어 기능 변경
- AI가 설비를 자동 정지하거나 정비명령을 자동 승인하는 기능
- 실제 기업의 생산·품질·개인정보 사용
- 상용 수준의 24시간 운영, 인증시험 및 현장배포
- 외부 생성형 AI 또는 예측 API의 단순호출을 이용한 핵심 고장예측 구현
- ERP, MES, CMMS 전체 기능의 대체

## 9. 가정 및 제약조건

### 9.1 주요 가정

- 대상 설비에는 필요한 센서가 설치되어 있거나 합성데이터로 대체할 수 있다.
- 각 센서와 설비에는 고유 식별자가 부여된다.
- Gateway는 센서 데이터를 표준 메시지로 변환할 수 있다.
- 교육용 데이터에는 민감한 생산·개인정보가 포함되지 않는다.
- 작업자와 정비 담당자는 기본적인 Dashboard 사용교육을 받는다.

### 9.2 주요 제약

- 5주 수업에서 요구사항, 아키텍처, OSS 선정까지 수행한다.
- GitHub 웹 편집기 중심으로 협업하며 Clone, Fork, GitHub Desktop은 사용하지 않는다.
- `main` Branch 직접수정을 금지하고 팀장이 Merge한다.
- AI 핵심모델은 후속 구현 Sprint에서 학생이 직접 개발·평가한다.
- OSS 선정은 기능뿐 아니라 License, 보안, Community, 업데이트 및 운영성을 고려해야 한다.

## 10. 성공 및 종료기준

- 프로젝트 정의, CONOPS, User Class 및 운용 시나리오가 승인된다.
- 기능·비기능·인터페이스 요구사항이 ID, 우선순위 및 검증방법을 포함한다.
- 비기능 요구사항이 실제 측정 가능한 수치로 작성된다.
- 요구사항이 시나리오와 이해관계자 필요로 추적된다.
- 3주차 아키텍처 설계를 시작할 수 있는 요구사항 기준선이 설정된다.
- Issue #2 관련 Pull Request Review와 Merge가 완료된다.
