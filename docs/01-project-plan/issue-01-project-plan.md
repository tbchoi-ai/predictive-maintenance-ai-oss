## 2. 프로젝트 개요

본 프로젝트는 제조설비에서 발생하는 진동, 온도, 전류, 압력 등의 센서 데이터를 수집·저장·시각화하고, 수집된 데이터를 이용하여 AI 고장징후 예측모델을 개발·학습·평가하는 것을 목적으로 한다. 개발된 AI 모델은 설비 상태 모니터링 시스템에 적용하며, 이상 또는 고장징후가 탐지되면 Alert/Warning을 발생시키고 운용자와 정비담당자가 조기에 대응할 수 있도록 지원한다.

프로젝트는 Agile 방식의 Sprint 또는 Product Backlog를 사용하지 않는다. 프로젝트 추진계획 수립, 운용개념 및 요구사항 정의, 아키텍처 설계, 계층별 OSS 조사·평가·선정, AI 모델 개발, 시스템 통합검증, 최종 산출물 작성의 순서로 수행한다. 각 단계는 사전에 정의된 산출물과 검토·승인 기준을 만족한 후 다음 단계로 진행한다.

---

## 3. Issue 목적

다음 활동의 기준이 되는 프로젝트 추진계획을 수립하고 팀원 간에 합의한다.

1. 프로젝트의 추진목표, 범위 및 수행방식을 명확하게 정의한다.
2. 9개 Issue를 기준으로 작업분할구조와 단계별 일정을 수립한다.
3. 팀원의 역할, 책임, 보고 및 의사결정 체계를 정의한다.
4. 단계별 산출물, 검토방법 및 완료·승인 기준을 정의한다.
5. GitHub Repository, Branch, Commit, Pull Request 및 형상관리 규칙을 수립한다.
6. 예상 위험요인을 식별하고 대응방안을 계획한다.

## 4. 적용 개발방식 및 추진원칙

### 4.1 적용 개발방식

- 계획 중심의 단계적 개발 방식을 적용한다.
- Sprint, Product Backlog, Sprint Backlog 및 Velocity는 사용하지 않는다.
- 요구사항은 사용자 유형을 식별하는 User Class 방식을 적용한다.
- 요구사항은 기능 요구사항, AI 요구사항, 비기능 요구사항, 데이터 요구사항 및 외부 인터페이스 요구사항으로 구분한다.
- 각 요구사항에는 고유 식별번호와 정량적 검증기준을 부여한다.
- OSS는 아키텍처 계층별로 후보군을 조사한 후 사전에 승인된 기준으로 평가·선정한다.
- AI 모델은 단순 조사에 그치지 않고 데이터 전처리, 학습, 평가, 시스템 적용 및 경보 연동까지 수행한다.
- 단계별 검토 결과가 승인된 후 후속 단계로 진행한다.

### 4.2 단계 전환 원칙

| 단계 | 주요 산출물 | 다음 단계 진행 조건 |
|---|---|---|
| 프로젝트 계획 | 프로젝트 추진계획서 | 일정, 역할, 산출물 및 관리방법 승인 |
| 프로젝트 정의 | 프로젝트 개요, 문제·목표·범위 | 프로젝트 범위와 제외범위 승인 |
| 운용개념 정의 | User Class, 운용 시나리오 | 핵심 사용자와 운용 흐름 승인 |
| 요구사항 정의 | 요구사항 명세서 | 요구사항의 완전성·추적성·검증 가능성 확인 |
| 아키텍처 설계 | 계층 구조, 인터페이스, 배치 구조 | 요구사항과 아키텍처 간 추적성 확인 |
| OSS 조사·선정 | Long List, Short List, 평가표 | 평가근거와 라이선스 적합성 승인 |
| AI 개발·통합 | 학습모델, 평가결과, 경보 연동 기능 | 성능기준 및 통합시험 통과 |
| 최종 완료 | 최종보고서, 시연자료, 위험·보완계획 | 산출물 검토와 최종 시연 승인 |

## 5. 세부 수행작업

### Task 1. 프로젝트 추진 기준 확정

- [ ] 프로젝트 명칭과 최종 목적을 확정한다.
- [ ] 개발 방식이 계획 중심의 단계적 방식임을 명시한다.
- [ ] 프로젝트 수행기간과 주요 검토시점을 확정한다.
- [ ] 교수자, 팀장, 요구사항 담당, 아키텍처 담당, OSS 조사 담당, AI·데이터 담당, 통합·시험 담당의 역할을 정의한다.
- [ ] 단계별 승인권자와 의사결정 방법을 정의한다.

### Task 2. 프로젝트 범위 초안 수립

- [ ] 설비 센서데이터 수집·저장·조회 범위를 정한다.
- [ ] 실시간 또는 준실시간 상태 모니터링 범위를 정한다.
- [ ] AI 학습데이터 준비, 모델 학습, 평가 및 배포 범위를 정한다.
- [ ] Alert/Warning 발생 및 조기 대응 절차의 구현 범위를 정한다.
- [ ] 교육용 시범과제에서 제외할 범위를 정의한다.

### Task 3. 작업분할구조 수립

- [ ] 전체 프로젝트를 Issue #1부터 #9까지의 작업 패키지로 구성한다.
- [ ] 각 Issue의 입력자료, 수행활동, 산출물, 담당자 및 완료기준을 정의한다.
- [ ] Issue 간 선후행 관계를 `Relationships`에 설정한다.
- [ ] 각 Issue를 해당 Project 및 Milestone에 연결한다.

### Task 4. 전체 일정 및 검토계획 수립

- [ ] Issue별 착수·완료 목표 주차를 정의한다.
- [ ] M1부터 M4까지 단계별 Milestone을 설정한다.
- [ ] 요구사항 검토, 아키텍처 검토, OSS 선정 검토, AI 모델 성능검토 및 최종검토 일정을 수립한다.
- [ ] 일정 지연 발생 시 보고, 영향분석 및 계획 변경 절차를 정의한다.

### Task 5. 산출물 및 품질관리 계획 수립

- [ ] 단계별 필수 산출물과 파일 위치를 정의한다.
- [ ] 문서명, 파일명, 요구사항 식별번호 및 버전 표기 규칙을 정의한다.
- [ ] 검토자, 검토항목, 승인방법 및 수정조치 기록방법을 정의한다.
- [ ] 요구사항-아키텍처-OSS-AI 모델-시험결과 간 추적방법을 정의한다.

### Task 6. GitHub 형상 및 협업관리 계획 수립

- [ ] `main`, `develop`, 작업 Branch의 용도를 정의한다.
- [ ] 작업자는 자신의 Branch에서만 파일을 작성·수정하도록 정한다.
- [ ] 작업 결과는 Pull Request를 통해 `develop`에 병합하도록 정한다.
- [ ] `develop`에서 검증된 결과만 최종적으로 `main`에 병합하도록 정한다.
- [ ] Commit 메시지와 Pull Request 작성 규칙을 정의한다.
- [ ] Issue와 Branch 및 Pull Request를 `Development`에 연결한다.

### Task 7. 위험관리 및 변경관리 계획 수립

- [ ] 데이터 부족, 데이터 품질 저하, 클래스 불균형 위험을 식별한다.
- [ ] AI 모델의 성능 미달 및 과적합 위험을 식별한다.
- [ ] OSS 라이선스 충돌, 보안 취약점, 유지보수 중단 위험을 식별한다.
- [ ] 센서·네트워크 장애와 경보 오탐·미탐 위험을 식별한다.
- [ ] 위험별 발생 가능성, 영향도, 담당자, 예방조치 및 대응조치를 기록한다.
- [ ] 요구사항·범위·일정 변경 요청의 제출, 영향분석, 승인 및 반영절차를 정의한다.

## 10. GitHub 작업 및 PR 규칙

### Branch 구성

```text
main
└── develop
    └── planning/project-plan
```

### 작업 절차

1. `develop`을 기준으로 `planning/project-plan` Branch를 생성한다.
2. 프로젝트 추진계획 파일을 작성하고 팀 내부검토 결과를 반영한다.
3. 변경 파일을 Commit하고 원격 Repository에 Push한다.
4. Pull Request를 다음과 같이 생성한다.

```text
base: develop  ←  compare: planning/project-plan
```

5. PR 설명에 `Relates to #1`을 입력한다.
6. 검토의견을 반영하고 승인 후 `develop`에 병합한다.
7. 교수자 승인과 완료기준 충족 여부를 확인한 후 Issue #1을 Close한다.

### Commit 메시지 예시

```text
docs: add project execution plan for predictive maintenance system
```

### Pull Request 제목 예시

```text
[Issue #1] 프로젝트 추진계획서 작성
```
