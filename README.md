# AI 기반 설비 상태 모니터링 및 예지보전 시스템

> 교수자 시범 프로젝트: Open Source를 활용한 SW 개발방법론

## 1. 프로젝트 개요

본 프로젝트는 생산설비에서 발생하는 온도, 진동, 전류, 압력 및 회전속도 등의 센서 데이터를 수집·저장·시각화하고, 정상 운전 데이터를 학습하여 설비의 이상 및 고장 징후를 사전에 예측하는 **AI 기반 설비 상태 모니터링 및 예지보전(Predictive Maintenance) 시스템**을 개발하는 것을 목표로 한다.

시스템은 단순한 임계치 초과 감시뿐 아니라 데이터의 변화 추세와 정상 패턴 이탈 정도를 분석한다. 이상 징후가 발견되면 심각도에 따라 `Warning` 또는 `Alert`를 발생시키고, 담당자가 점검·정비·운전조건 조정 등의 조기 대응을 수행하고 그 결과를 기록할 수 있도록 지원한다.

이 프로젝트는 완성된 상용 시스템 개발보다 다음의 교육 활동에 중점을 둔다.

- 프로젝트 요구사항 정의
- 논리·물리 아키텍처 설계
- 시스템 계층별 필요 기능 식별
- GitHub를 활용한 OSS 검색 및 후보군 관리
- 객관적 기준에 따른 OSS 비교·평가·선정
- 핵심 기능의 PoC 구현
- OSS 라이선스·보안·성숙도 검토
- 선정 근거와 의사결정 과정의 문서화

---

## 2. 배경 및 문제 정의

생산설비의 고장은 생산중단, 품질저하, 정비비 증가 및 안전사고로 이어질 수 있다. 기존의 사후정비는 고장이 발생한 후 조치하므로 손실을 예방하기 어렵고, 주기적인 예방정비는 설비 상태와 무관하게 부품을 교체하여 불필요한 비용을 발생시킬 수 있다.

본 프로젝트는 센서 데이터에 기반하여 설비 상태를 지속적으로 관찰하고 고장으로 발전할 가능성이 있는 이상 징후를 조기에 발견함으로써 다음 문제를 해결하고자 한다.

1. 설비의 현재 상태를 실시간으로 파악하기 어렵다.
2. 센서 데이터가 분산되어 있어 종합적인 분석이 어렵다.
3. 이상 징후를 작업자의 경험에만 의존하여 판단한다.
4. 경미한 이상이 실제 고장으로 진행되는 과정을 추적하기 어렵다.
5. 경보 발생 후 점검·정비·종결 과정이 체계적으로 관리되지 않는다.

## 3. 프로젝트 목표

### 3.1 최종 목표

센서 데이터 수집부터 이상 징후 예측, 경보 발생 및 조기 대응관리까지 연결되는 예지보전 시스템의 MVP를 구축한다.

### 3.2 세부 목표

- 설비 및 센서 등록·관리
- 센서 데이터의 실시간 또는 주기적 수집
- 센서 데이터의 저장·조회·시각화
- 정상 운전 데이터 학습 및 기준 패턴 생성
- 임계치 기반 상태 감시
- AI/ML 기반 이상 징후 탐지 및 사전예측
- `Normal`, `Warning`, `Alert` 상태 분류
- 이상 징후 발생 시 담당자 통보
- 점검·정비·운전조정 등 조기 대응업무 관리
- 경보 발생부터 종결까지의 이력 추적
- 계층별 OSS 후보 비교 및 최종 선정

## 4. 프로젝트 범위

### 4.1 포함 범위

- 가상 설비 2~3대 구성
- 설비당 3개 이상의 센서 데이터 사용
- 온도, 진동, 전류, 압력, 회전속도 중 필요한 센서 선택
- 센서 시뮬레이터 또는 공개 데이터셋 사용
- 실시간 또는 일정 주기의 데이터 수집
- 시계열 데이터 저장 및 조회
- 설비 상태 Dashboard 제공
- 정상 패턴 학습 및 이상 점수 산출
- Warning 및 Alert 판단
- 이메일, 메시지 또는 화면 경보 제공
- 대응업무 등록·할당·처리·종결
- 사용자 인증과 역할별 권한관리의 기본 기능
- OSS 후보 검색, 평가, PoC 및 선정 결과 문서화

### 4.2 제외 범위

- 실제 공장 PLC와의 직접 연동
- 실제 생산설비의 자동 정지 또는 원격제어
- 안전인증이 요구되는 실시간 제어 기능
- 대규모 공장 전체의 상용 수준 운영
- 고장 시점의 절대적 보장
- 작업자 확인 없이 AI가 독자적으로 수행하는 정비 의사결정

| 시스템 관리자 | 사용자·권한·서비스·보안·로그·백업 관리 |

## 6. 핵심 운용 시나리오

1. 센서 시뮬레이터가 설비의 온도·진동·전류 데이터를 생성한다.
2. 데이터 수집 서비스가 센서 데이터를 수신하고 유효성을 검사한다.
3. 검증된 데이터가 시계열 데이터베이스에 저장된다.
4. Dashboard가 설비별 현재값과 변화 추세를 표시한다.
5. 정상 운전 데이터로 학습된 모델이 새로운 데이터의 이상 점수를 산출한다.
6. 규칙 엔진이 임계치, 지속시간, 이상 점수를 종합하여 상태를 판정한다.
7. 이상 가능성이 낮으면 `Normal`, 주의가 필요하면 `Warning`, 즉각적인 확인이 필요하면 `Alert`를 발생시킨다.
8. 시스템은 설비 운영자 또는 정비 담당자에게 경보를 전달한다.
9. 담당자는 현장 확인, 운전조건 조정, 부품점검 또는 예방정비를 수행한다.
10. 담당자는 조치내용과 결과를 등록하고, 관리자는 경보를 종결한다.
11. 조치결과는 향후 모델 개선과 정비정책 수립에 활용한다.

## 7. 설비 상태 및 경보 정의

| 상태 | 의미 | 예시 조건 | 기본 대응 |
|---|---|---|---|
| `Normal` | 정상 운전 범위 | 센서값과 이상 점수가 정상 범위 | 지속 모니터링 |
| `Warning` | 이상 가능성 또는 성능저하 징후 | 임계치 근접, 완만한 상승, 이상 점수 증가 | 운영자 확인, 추세관찰, 점검계획 수립 |
| `Alert` | 고장 가능성이 높거나 즉각적인 확인 필요 | 임계치 초과 지속, 급격한 변화, 높은 이상 점수 | 정비 담당자 통보, 긴급점검, 필요 시 운전중지 검토 |

경보는 한 번의 순간적인 측정값만으로 확정하지 않고 다음 정보를 종합하여 판단하는 것을 권장한다.

- 센서값의 임계치 초과 여부
- 임계치 초과 지속시간
- 일정 시간 동안의 변화율
- 여러 센서 간 상관관계
- AI/ML 모델의 이상 점수
- 동일 설비에서 최근 발생한 경보 이력

> 본 시스템의 예측결과와 Alert는 의사결정을 지원하는 정보이며, 실제 설비 정지 및 정비 여부는 권한을 가진 담당자가 결정한다.

## 8. 주요 기능 요구사항

### FR-01. 설비 및 센서 관리

- 관리자는 설비를 등록·수정·조회할 수 있어야 한다.
- 관리자는 설비별 센서 종류, 단위, 정상범위 및 임계치를 설정할 수 있어야 한다.

### FR-02. 센서 데이터 수집

- 시스템은 센서 시뮬레이터 또는 파일로부터 데이터를 수집할 수 있어야 한다.
- 시스템은 수집시간, 설비 ID, 센서 ID, 측정값과 품질상태를 기록해야 한다.
- 시스템은 누락값, 중복값 및 비정상 형식 데이터를 식별해야 한다.

### FR-03. 데이터 저장 및 조회

- 시스템은 센서 데이터를 시계열 형태로 저장해야 한다.
- 사용자는 설비·센서·기간을 조건으로 데이터를 조회할 수 있어야 한다.

### FR-04. 실시간 모니터링

- 사용자는 설비별 최신 상태와 센서값을 Dashboard에서 확인할 수 있어야 한다.
- 사용자는 센서 데이터의 시간대별 변화 추세를 확인할 수 있어야 한다.

### FR-05. 정상 패턴 학습

- 데이터 분석가는 정상 운전 데이터를 선택하여 학습데이터셋을 구성할 수 있어야 한다.
- 시스템은 학습 모델의 버전, 학습일자, 데이터 범위 및 평가결과를 기록해야 한다.

### FR-06. 이상 징후 탐지 및 예측

- 시스템은 신규 센서 데이터에 대해 이상 점수를 계산해야 한다.
- 시스템은 임계치 방식과 AI/ML 방식의 결과를 함께 사용할 수 있어야 한다.
- 시스템은 이상 판정에 사용한 주요 근거를 제공해야 한다.

### FR-07. Warning 및 Alert 관리

- 시스템은 판정결과에 따라 Warning 또는 Alert를 생성해야 한다.
- 경보에는 설비, 발생시간, 심각도, 관련 센서값, 이상 점수 및 판정근거가 포함되어야 한다.
- 동일 원인으로 반복 발생하는 경보는 중복 억제 또는 통합할 수 있어야 한다.

### FR-08. 알림

- 시스템은 담당자에게 화면, 이메일 또는 메시지 방식으로 알림을 전송할 수 있어야 한다.
- 사용자는 알림 수신 여부를 확인 처리할 수 있어야 한다.

### FR-09. 조기 대응관리

- 담당자는 경보에 대해 점검업무를 생성할 수 있어야 한다.
- 점검업무에는 담당자, 우선순위, 예정일, 조치내용 및 처리상태가 포함되어야 한다.
- 처리상태는 `Open`, `Assigned`, `In Progress`, `Resolved`, `Closed`로 관리할 수 있어야 한다.
- 담당자는 점검·운전조정·부품교체 등의 조치결과를 등록할 수 있어야 한다.

### FR-10. 이력 및 보고서

- 사용자는 경보 발생부터 조치·종결까지의 전체 이력을 조회할 수 있어야 한다.
- 관리자는 기간별 Warning·Alert 발생 건수와 평균 처리시간을 확인할 수 있어야 한다.

### FR-11. 사용자 및 권한관리

- 시스템은 사용자 인증 기능을 제공해야 한다.
- 역할에 따라 조회, 설정, 조치 및 관리자 기능의 접근권한을 구분해야 한다.

| 성능 | 센서 데이터 수신 후 설정된 시간 이내에 Dashboard에 반영되어야 한다. |
| 가용성 | 개별 분석서비스 장애가 원본 센서 데이터의 손실로 이어지지 않아야 한다. |

| 무결성 | 센서 데이터와 경보·조치 이력은 임의 변경 여부를 추적할 수 있어야 한다. |
| 설명가능성 | Warning과 Alert에 사용된 센서 및 판정근거를 제시해야 한다. |

| 상호운용성 | 외부 시스템 연계를 위한 표준 API 또는 메시지 인터페이스를 제공해야 한다. |
| 관측가능성 | 서비스 상태, 오류, 처리량 및 지연시간을 로그와 지표로 확인할 수 있어야 한다. |
| 이식성 | 컨테이너 기반 실행환경을 고려하여 특정 운영환경 의존성을 줄여야 한다. |

구체적인 목표값은 요구사항 분석 및 PoC 환경 측정 후 확정한다.

        v

                   v

## 15. GitHub 협업 방법

### 15.1 권장 Branch

| 역할·기능 | Branch 예시 |
|---|---|
| 데이터 수집 | `feature/data-ingestion` |
| 센서 시뮬레이터 | `feature/sensor-simulator` |
| 데이터 저장 | `feature/time-series-storage` |
| 이상탐지 모델 | `feature/anomaly-detection` |
| Dashboard | `feature/monitoring-dashboard` |
| 경보·대응관리 | `feature/alert-response` |
| OSS 평가 문서 | `docs/oss-evaluation` |

### 15.2 작업 절차

1. Product Backlog와 OSS 조사 항목을 GitHub Issue로 등록한다.
2. 담당자는 Issue를 자신에게 할당한다.
3. Issue 번호가 포함된 Branch를 생성한다.
4. 조사결과, 문서 또는 코드를 Commit한다.
5. Pull Request를 생성하고 관련 Issue를 연결한다.
6. 팀원이 요구사항·근거·라이선스·보안·통합성을 Review한다.
7. Review 결과를 반영한 후 `develop` 또는 `main`에 Merge한다.
8. 주요 OSS 선정은 ADR로 남긴다.

### 15.3 Commit 예시

```text
docs: define sensor data requirements
docs: compare MQTT broker candidates
feat: add vibration sensor simulator
feat: implement anomaly score API
test: add warning threshold tests
fix: prevent duplicate alert generation
```

## 18. MVP 완료조건(Definition of Done)

- [ ] 가상 설비 2대 이상과 센서 3종 이상의 데이터가 생성된다.

## 22. 프로젝트 핵심 성공기준

본 프로젝트의 성공은 가장 복잡한 AI 모델을 사용하는 데 있지 않다. 다음의 전체 흐름이 일관되게 연결되고, 각 OSS의 선정 근거가 객관적으로 설명되는 것이 핵심이다.

> 센서 데이터 수집 → 저장·시각화 → 정상 패턴 학습 → 이상 징후 예측 → Warning/Alert → 담당자 확인 → 조기 대응 → 결과 기록 및 개선
