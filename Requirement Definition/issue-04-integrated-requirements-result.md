## 1. 문서 목적

본 문서는 User Class와 운용 시나리오를 구현·시험 가능한 시스템 요구사항으로 변환하는 것을 목적으로 한다. 요구사항은 다음 다섯 종류로 구분한다.

1. 기능 요구사항(`FUN`)
2. AI 요구사항(`AIR`)
3. 데이터 요구사항(`DAT`)
4. 인터페이스 요구사항(`INT`)
5. 비기능 요구사항(`NFR`)

각 요구사항에는 고유 식별번호, 요구문, 출처 User Class 또는 시나리오, 우선순위와 검증방법을 부여한다.

## 2. 요구사항 작성·관리 원칙

### 2.1 요구사항 문장 원칙

- 요구사항은 `시스템은 ～하여야 한다` 형식으로 작성한다.
- 하나의 요구사항에는 가능한 한 하나의 검증대상만 포함한다.
- `빠르게`, `충분히`, `적절하게`와 같은 주관적 표현을 사용하지 않는다.
- 성능, 용량, 시간, 정확도 및 보안수준은 수치로 표현한다.
- 구현방법이나 특정 OSS 제품을 불필요하게 지정하지 않는다.
- 요구사항은 시험, 분석, 시연 또는 검사로 검증 가능해야 한다.

### 2.2 우선순위

| 우선순위 | 의미 |
|---|---|
| Must | MVP Release에 반드시 포함 |
| Should | 중요하지만 일정·위험에 따라 다음 Release로 조정 가능 |
| Could | 여력이 있을 때 구현 |
| Won't | 현재 MVP에서 구현하지 않음 |

### 2.3 검증방법

| 기호 | 검증방법 | 설명 |
|---|---|---|
| T | Test | 시험입력과 기대결과를 이용한 동적 시험 |
| D | Demonstration | 실제 사용자 흐름을 실행하여 시연 |
| A | Analysis | 측정값, 모델성능, 로그 또는 계산결과 분석 |
| I | Inspection | 문서, 코드, 구성, 라이선스 또는 설정 검사 |

### 2.4 요구사항 변경상태

| 상태 | 의미 |
|---|---|
| Proposed | 신규 제안, 검토 전 |
| Approved | Product Owner 승인 |
| Implemented | 구현 완료 |
| Verified | 검증 완료 |
| Deferred | 후속 Release로 연기 |
| Rejected | 검토 후 미채택 |

## 4. 시스템 범위 및 기준 운용조건

### 4.1 MVP 기준규모

| 항목 | 기준값 |
|---|---:|
| 등록 설비 | 최대 20대 |
| 설비당 센서 | 최대 10개 |
| 전체 등록 센서 | 최대 200개 |
| 필수 센서 종류 | 온도·진동·전류 등 최소 3종 |
| 지속 입력 처리량 | 초당 100건 이상 |
| 동시 접속 사용자 | 10명 이상 |
| 시계열 데이터 보존 | 최소 90일 |
| 감사로그 보존 | 최소 180일 |
| 기준 시험환경 | 4 Core CPU, RAM 8GB, 사용 가능 저장공간 20GB 이상 |

### 4.2 AI 상태분류

| 상태 | 초기 위험점수 기준 | 의미 |
|---|---:|---|
| Normal | `0.00 ≤ score < 0.60` | 정상 감시 지속 |
| Warning | `0.60 ≤ score < 0.80` | 조기점검 또는 관찰 필요 |
| Alert | `0.80 ≤ score ≤ 1.00` | 신속한 확인과 정비대응 필요 |

> 0.60과 0.80은 초기 기본값이다. 최종 임계값은 검증데이터의 Precision-Recall 결과와 사용자 피드백을 근거로 조정할 수 있다. 변경된 임계값과 근거는 버전관리하고 `Warning threshold < Alert threshold` 관계를 항상 유지한다.

## 13. 요구사항 변경관리

1. 변경 제안자는 GitHub에 `type: requirement-change` Issue를 생성한다.
2. 변경 Issue에 대상 요구사항 ID, 변경 전·후 내용, 사유와 기대효과를 작성한다.
3. 팀은 User Class, 아키텍처, OSS, 일정, AI 모델, 시험과 라이선스 영향을 분석한다.
4. Product Owner가 승인, 연기 또는 거부를 결정한다.
5. 승인된 변경은 적용 Sprint와 담당자를 지정한다.
6. 요구사항 문서, Product Backlog, 아키텍처와 시험 Case를 함께 갱신한다.
7. PR Review와 Sprint Review에서 변경 반영 여부를 확인한다.


### Pull Request 설정

```text
base: develop  ←  compare: docs/4-integrated-requirements
```

```text
docs: add integrated functional AI and nonfunctional requirements
```

### Pull Request 제목 예시

```text

```
